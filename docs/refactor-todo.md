# Phalanx 重构与修复待办清单

## 目标

本次重构的核心目标是：

- 严格区分 `server` 与 `client` 的职责
- 减少多人模式下不必要的同步与卡顿
- 统一工具、车载、CIWS、无人机的逻辑结构
- 修复当前已经确认的战斗逻辑与交互问题

## 总体原则

### Server 负责

- 权威状态
- 输入判定后的真实开火
- 炮塔姿态与 AI 逻辑
- 弹道、命中、伤害、爆炸
- 生成与销毁实体
- 多人同步所需的最少事件

### Client 负责

- 相机
- UI 与准星
- 音效、震动、枪口火光、曳光、烟雾
- 闪烁灯、导航灯、信标、轮廓等纯表现
- 本地视觉预测与渲染

### Shared 负责

- 纯配置
- 纯算法
- 与具体工具/载具无关的公共逻辑

## 第一部分：结构重构任务

### 1. 明确 server/client 边界

- 为工具、车载、CIWS、无人机分别定义 server 和 client 的职责边界
- 补充文档，记录哪些逻辑必须放在 server，哪些逻辑只能放在 client
- 避免同一个状态在 server 和 client 两边重复维护

### 2. 重构 shared 武器模块

- 整理 `shared/phalanx_weapon/` 下各模块职责
- 将“真实武器逻辑”和“纯视觉表现”分离
- 避免 shared 模块直接依赖具体载具、工具、相机、玩家上下文

建议方向：

- `phalanx_weapon_config.lua`
  只放参数与配置
- `phalanx_weapon_projectile.lua`
  只放服务端弹道、命中、爆炸
- `phalanx_weapon_fx.lua`
  只放客户端特效
- `phalanx_weapon_audio.lua`
  只放客户端音效
- `phalanx_weapon_spin.lua`
  拆为服务端状态与客户端表现两部分

### 3. 统一工具 / 车载 / CIWS 的开火链路

- 统一开火输入到“请求开火 -> 服务端验证 -> 服务端生成真实弹道”
- 统一开火表现到“客户端接收事件 -> 播放音效与特效”
- 减少三套脚本中重复且不一致的逻辑

涉及文件：

- `tool/phalanx/phalanx.lua`
- `vehicle/phalanx-truck/phalanx_truck.lua`
- `vehicle/ciws/ciws_emplacement.lua`

### 4. 拆分 AI CIWS 与玩家 CIWS

- 将 AI 版和玩家可操作版 CIWS 拆成两个独立脚本
- 将 AI 版和玩家版的 XML 也拆分
- 减少单脚本里大量 `isAi` 分支

建议目标：

- `ciws_player_emplacement.lua`
- `ciws_ai_emplacement.lua`
- 玩家版 XML 保留 `seat/player/camera/rig`
- AI 版 XML 去掉玩家进入相关内容

### 5. 建立统一调试开关

- 将当前散落在各处的 `DebugPrint` / `DebugWatch` 收口
- 提供统一调试配置开关
- 支持按系统开启或关闭调试输出

建议调试分类：

- `debug.projectile`
- `debug.ai`
- `debug.camera`
- `debug.drone`
- `debug.network`
- `debug.fx`

### 6. 建立最小验证场景

- 保留最小化 demo，方便每次重构后快速验证
- 避免每次都在完整地图中排查问题

建议保留：

- 按钮生成无人机 demo
- 单门 AI CIWS demo
- 玩家控制 CIWS demo
- 手持武器开火 demo

## 第二部分：待修复 Bug 列表

### Bug 1：高角度时子弹方向切换到玩家视角

现象：

- 当玩家视角与密集阵炮口夹角较大时，子弹方向会偏向玩家视角
- 角度较小时，此问题不明显

影响：

- 炮口指向与真实弹道不一致
- 玩家观感错误
- 命中逻辑不稳定

初步判断：

- 服务端最终开火方向并非严格来自炮口指向
- 可能直接或间接使用了玩家相机 forward
- 高角度时，相机方向与炮口方向偏差被放大

修复方向：

- 服务端先确定目标点
- 再使用“炮口位置 -> 目标点”计算最终弹道方向
- 不直接把玩家视角 forward 当作子弹方向
- 炮塔姿态解算与弹道方向解算使用同一套权威数据

优先级：

- 高

### Bug 2：AI 密集阵不应允许玩家进入

现象：

- AI CIWS 仍然可能允许玩家进入或接管

影响：

- AI 版与玩家版职责混乱
- 后续逻辑判断复杂度上升

初步判断：

- AI 与玩家版共用了相同或过于接近的 XML / Lua
- AI 版仍保留了可进入的 `seat` / `rig` / `player` / `camera`

修复方向：

- 将 AI 版与玩家版 CIWS 完全拆分
- AI 版去掉所有玩家进入相关节点
- AI 版脚本不再处理玩家输入

优先级：

- 高

### Bug 3：多人模式开火时其他客户端明显卡顿

现象：

- 任意玩家开火时，其他客户端会明显卡顿
- 已验证与开火行为直接相关
- 手持、车载、CIWS 都会触发

影响：

- 多人体验严重下降
- 后续功能调试受到干扰

初步判断：

- 当前投射物同步方式过重
- 服务端可能在每一发子弹、每一帧都向客户端发 RPC
- 客户端可能重复处理过多的音效、粒子、曳光或 Debug 输出

重点可疑位置：

- `shared/phalanx_weapon/phalanx_weapon_projectile.lua`

修复方向：

- 停止逐发逐帧 `ClientCall`
- 改为同步“开火事件”和“命中事件”
- 客户端基于初速度本地模拟曳光、烟雾、枪口火光
- 音效与震动只在相关客户端或附近客户端触发
- 多人测试时默认关闭高频 `DebugWatch`

优先级：

- 最高

## 第三部分：推荐实施顺序

### 第一阶段：先处理多人性能

- 重构投射物同步方式
- 去掉逐弹逐帧的高频 RPC

原因：

- 统一目标点与炮口方向解算
- 修复视角方向错误介入弹道的问题

原因：

- 这是核心战斗正确性问题

### 第三阶段：拆分 AI CIWS 与玩家 CIWS

- 先拆脚本
- 再拆 XML
- 清理交叉逻辑

原因：

- 这是结构性优化，适合在基础性能与开火正确性稳定后进行

### 第四阶段：统一整体架构

- 统一工具 / 车载 / CIWS 的 server-client 模式
- 统一 shared 模块边界
- 清理重复代码

## 第四部分：后续执行规则

- 所有纯表现逻辑优先放到 client
- 所有真实状态与判定优先放到 server

## 第五部分：无人机后续架构规划

### 新需求：增加玩家可驾驶的非 AI 无人机版本

目标：

- 在现有 AI 无人机之外，增加一个玩家可进入、可驾驶、可按玩家视角飞行和转向的版本
- 玩家版无人机应支持第一人称/第三人称视角切换或至少保留玩家视角驱动的飞行方式
- 玩家版与 AI 版的逻辑应尽量复用公共飞行模块，但入口与实体结构分离

### 为什么当前 demo 结构不适合作为最终落点

当前 AI 无人机主要位于：

- `demo/drone_target.lua`
- `demo/drone_target.xml`

这套结构更适合：

- 场景按钮生成测试
- AI 靶机 / 靶标
- 地图内 demo 逻辑

不适合作为最终玩家可驾驶无人机的原因：

- `demo/` 更偏向测试和场景验证，不适合作为正式载具入口
- 玩家可驾驶实体应当按照载具体系来组织
- 后续如果要支持相机、座位、输入、网络同步，放在 `vehicle/` 下更清晰

### 无人机建议拆分方向

建议将无人机拆成两类：

1. AI 无人机
2. 玩家无人机

建议目录方向：

- `vehicle/drone/drone_player.lua`
- `vehicle/drone/drone_player.xml`
- `vehicle/drone/drone_ai.lua`
- `vehicle/drone/drone_ai.xml`

如果需要共享飞行逻辑，建议再抽公共模块，例如：

- `shared/drone/drone_flight_common.lua`
- `shared/drone/drone_visual_common.lua`

### AI 无人机职责

- 作为 CIWS 目标或测试靶机
- 自动巡航 / 自动机动
- 服务端控制真实飞行与销毁
- 客户端只负责闪烁信标、拖尾、可视表现

### 玩家无人机职责

- 玩家可进入与驾驶
- 飞行方向受玩家视角控制
- 机体姿态根据玩家输入和视角进行联动
- 支持相机、座位、输入、多人同步
- 服务端负责真实姿态与移动
- 客户端负责相机、UI、特效、提示与纯表现

### 玩家无人机待办任务

#### 1. 迁移到 `vehicle/` 体系

- 新建 `vehicle/drone/`
- 将玩家版无人机 XML 和 Lua 放入该目录
- 不再继续把正式玩家无人机逻辑放在 `demo/`

#### 2. 设计玩家无人机 XML 结构

- 增加玩家可进入的 `rig`
- 增加 `seat`
- 增加 `camera`
- 预留必要的 `player` / `vital` / 输入定位节点

#### 3. 设计玩家视角驱动的飞行控制

- 玩家视角决定无人机目标朝向
- 服务端根据目标朝向更新真实机体姿态
- 需要处理俯仰、偏航、横滚之间的联动
- 需要避免视角方向与机体速度方向完全脱节

#### 4. 评估 AI 与玩家无人机的共享模块边界

建议共享：

- 基础飞行数学
- 平滑旋转
- 高度保持/速度限制
- 公共视觉效果

建议分离：

- AI 巡航逻辑
- 玩家输入逻辑
- 相机逻辑
- 进入/退出逻辑
- 网络同步接口

#### 5. 重新定义 demo 无人机的定位

保留 `demo/drone_target.*`，但只作为：

- 场景按钮测试目标
- AI 靶机
- 最小验证版本

不要再把它当成最终正式无人机的长期入口。

### 无人机相关新增 Bug / 风险

#### 风险 1：玩家版与 AI 版混在同一脚本内会迅速失控

影响：

- 条件分支过多
- 相机、输入、AI、网络状态互相污染

结论：

- 玩家版与 AI 版必须拆脚本、拆 XML

#### 风险 2：玩家视角飞行若直接在客户端驱动，可能造成多人不同步

影响：

- 机体位置与姿态在多人中不一致
- 命中和碰撞判定不可靠

结论：

- 玩家输入可以在客户端采集
- 真实飞行状态必须由服务端权威更新

#### 风险 3：玩家无人机未来可能复用 CIWS 武器系统，需提前考虑共享边界

影响：

- 若边界不清晰，会再次出现工具/车载/CIWS 那种重复逻辑

结论：

- 后续如玩家无人机也具备武器，应优先复用重构后的 shared 武器核心

### 无人机模块的推荐实施顺序

1. 先保留当前 `demo/drone_target.*` 作为稳定 AI 靶机版本
2. 在 `vehicle/drone/` 下建立玩家无人机最小骨架
3. 先实现进入、相机、基本飞行，不急着加武器
4. 再抽取 AI/玩家共享飞行模块
5. 最后再决定是否给玩家无人机增加武器系统
